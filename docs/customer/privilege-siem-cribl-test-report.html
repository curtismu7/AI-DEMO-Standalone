Summary

  • PingOne Privilege's SIEM setting can send to Elasticsearch through Cribl Stream, using either a username and password or an API key. Events arrive masked, tagged and searchable, in the index you choose.
  • Everything that was planned was tested and works, with the limits listed below. The two that matter most: there is no queue by default (events are lost while Elasticsearch is down or the pipeline restarts), and the SIEM holds your sealed prompt records, so protect the index and the private key together.
  • Prompt logging reaches the SIEM sealed. In a control test with a real prompt, no part of the prompt appeared in any event; the content arrived only as ciphertext, with the user, agent, app and request id in the clear.
  • Not completed: opening a real sealed record end to end (it needs the private key for the tenant's key and the record layout, which is not published). Other items not tested are listed in section 7.

Scope and method

In scope: delivering Privilege's SIEM events to Elasticsearch through Cribl Stream; the two authentication options; masking and enrichment in Cribl; least-privilege access; the optional gateway log path; and what the SIEM receives when prompt logging is on.

Method: an automated local test (Cribl and nginx against stand-in Elasticsearch servers) with 54 checks, plus live runs against a test Privilege tenant, a live Cribl deployment and a live Elasticsearch, using real traffic from demo agents. Findings that shaped the design

FindingConsequence
Cribl's Elasticsearch source accepts only _bulk requests, and one authentication modePrivilege uses _bulk, so it works. nginx in front checks Basic or ApiKey and Cribl listens on loopback.
Cribl's source does not accept the ApiKey schemeThe nginx front also handles the API-key option.
Privilege names the index itself and the form has no Index fieldThe pipeline forces the destination index. The writer role only needs that index family.
A write-only user cannot make Cribl's startup version callName the Elasticsearch version in the destination.
Cribl's mask function stringifies every value it visitsHarmless for audit events; for events with real numbers, exclude those fields (before the wildcard, because the first match wins).
Long credential strings exceed nginx's default map bucketRaise map_hash_bucket_size.
Cribl regenerates its admin user as admin/admin when its configuration directory is emptyPersist the directory, or set the password from a secret on every start.
Events appear up to about a minute after the actionWait before concluding anything is missing.

Prompt logging: what the SIEM receives

The Prompt Logging page says that recorded prompts, tool calls and (optionally) responses are encrypted to a public key the customer holds, and that Privilege cannot read them. We checked what reaches the SIEM:

  • 159 records in 66 minutes of light demo traffic: 81 on LLM traffic, 42 agent-to-agent, 36 MCP. A request and its response are separate records; both carry the same encapsulated key.
  • In the clear: app, user, agent key, key type, principal kind, tenant, request id, direction, surface, size and the number of units.
  • Sealed: Content (ciphertext) and Enc, with Alg = HPKE-X25519-SHA256-AES256GCM-EXPORT and a KeyID naming the key.
  • Marker test: a real model call whose prompt contained a unique marker string. The marker was absent from the SIEM index, from both gateway-event stores and from the gateway's own log line, and sample words from the prompt were not visible in any record.
  • Key change: after the key was regenerated in the console, the next call's records carried a new key id. Each record names the key that sealed it, so old records need the old key.
What this means. The SIEM never receives the plaintext, but it does hold the encrypted content of every recorded prompt. Anyone who has the private key and can read the index can open all of it. Treat the index and the private key as one security domain, and keep the private key out of the SIEM's reach. Cribl does not alter the ciphertext.

Volume: about 2.4 records a minute here, at most about 3.4 KB each so far. The size limit allows up to 131,072 bytes per record, so plan retention and storage for real use.

Restrictions

  • No queue by default in Cribl: events are lost while Elasticsearch is down or the pipeline restarts. A persistent queue is possible (not tested here).
  • A short gap on each deploy of a single replica; two replicas with a rolling update would avoid it (not tested here).
  • Privilege sends from its cloud, so the endpoint must be reachable from the internet over HTTPS.
  • Cribl's Elasticsearch source is _bulk only and takes one authentication mode.
  • The index name is chosen by Privilege and cannot be set in the form; the pipeline overrides it.
  • Client IP addresses and a session identifier remain in gateway request events. Treat the index as sensitive.
  • Prompt-log events carry sealed content, user ids and agent names in the clear.

Recommendations

  1. Use the layout in the setup guide as is: nginx front, Cribl on loopback, a write-only Elasticsearch user.
  2. Decide on loss tolerance. If audit events must not be lost, enable a persistent queue and run two replicas before go-live.
  3. Generate every credential randomly, store it in a secret manager, and rotate it on a schedule; test the refusals after each rotation.
  4. Restrict who can read the index, and keep prompt-logging private keys apart from the SIEM.
  5. Size the index for prompt-log volume and set a retention policy before turning on more surfaces.
  6. Add the field names of any new numeric field to the mask exclusion list so it keeps its type.
  7. Re-run the verification steps after every Privilege, Cribl or Elasticsearch upgrade.

Not tested

  • Opening a real sealed prompt record end to end (needs the private key and the record layout).
  • The coding agents surface of prompt logging: no traffic of that kind was generated.
  • Alerting and dashboards on top of the events.
  • High availability, persistent queues, load and long-running volume.
  • Index lifecycle management and retention.
  • Other SIEM destinations through Cribl.
