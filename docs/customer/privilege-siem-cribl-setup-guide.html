What you will build

PingOne Privilege can send its audit and runtime events to Elasticsearch through its SIEM setting. This guide puts Cribl Stream in the middle, so that you can mask secrets, add fields that are easy to filter on, and route the same events to other destinations later.

PingOne Privilege (cloud)HTTPS, Basic or ApiKey →nginx: checks the credential→Cribl Stream: mask, add fields→Elasticsearch

What you get in Elasticsearch:

  • Console changes (who changed which app, policy or key), guardrail verdicts, policy decisions, accepted gateway requests and prompt-log records, each tagged by an Index field.
  • Secrets removed from the events before they are stored.
  • Top-level gw_* fields (user, agent key, policy ids, decision, target) so dashboards need no nested paths.

Tested with Cribl Stream 4.13, nginx 1.27 and Elasticsearch 9.1, with Privilege's SIEM provider set to Elastic. Names, hosts and credentials below are examples or placeholders: the user privilege, the role privilege_siem_writer, the writer cribl_siem, the index privilege-siem-events and the host siem.example.com are only suggestions. Use your own, consistently, in every step.

How Privilege sends events

Knowing the exact requests saves time. These are what was observed from the console's SIEM Config against a test endpoint. Privilege may change them in a release, so treat them as a guide and let the Health Check and step 7 tell you if something differs.

Step 1. Elasticsearch: a write-only user

Give Cribl the least access it needs: create documents in one index family and nothing else. Run as an administrator (Kibana Dev Tools or curl):

Elasticsearch
PUT _security/role/privilege_siem_writer
{
  "cluster": ["monitor"],
  "indices": [{
    "names": ["privilege-siem-events*"],
    "privileges": ["auto_configure", "create_index", "create_doc", "index", "view_index_metadata"]
  }]
}

PUT _security/user/cribl_siem
{ "password": "<generate-a-long-random-password>", "roles": ["privilege_siem_writer"] }
Why no read access. A writer that cannot read cannot leak what is already stored. Create a separate read-only role for the people who search the index. Do not use the built-in superuser for ingestion, and do not leave an anonymous role on the cluster.

The index privilege-siem-events is created on the first write. We use that name throughout; use your own if you prefer, in the role and in step 3.

Step 2. Create four secrets

Generate each value randomly and store it in your secret manager.

SecretUsed byHow to make it
Privilege login (user and password)Privilege signs in to your endpoint (Basic)User privilege; password: openssl rand -hex 24
Privilege API keyPrivilege signs in (ApiKey), if you choose that modeprintf 'siem:%s' "$(openssl rand -hex 24)" | base64 | tr -d '\n'. Keep it to the characters A-Z a-z 0-9 + / = _ - (it sits inside an nginx map).
Elasticsearch writer passwordCribl signs in to ElasticsearchThe password you set for cribl_siem in step 1.
Cribl admin passwordYou, in the Cribl UICribl requires 3 of 4 character classes (lower, upper, digit, symbol). Example: $(openssl rand -hex 20)-Aa.

Use either the login or the API key in Privilege, not both at once. Having both configured in nginx is harmless and lets you switch without a deployment.

Step 3. Cribl Stream

One source, one destination, one route and one pipeline. If you prefer the UI, create the same objects there; the YAML below is what Cribl stores under $CRIBL_HOME/local/cribl/.

Source: an Elasticsearch API source on loopback

inputs.yml
inputs:
  in_elastic:
    type: elastic
    disabled: false
    host: 127.0.0.1        # loopback only: nginx is the only way in
    port: 9201
    elasticAPI: /
    authType: none
    tls:
      disabled: true
    proxyMode:
      enabled: false

Destination: Elasticsearch

outputs.yml
outputs:
  es_siem:
    type: elastic
    url: 'https://<elasticsearch-host>:9200/_bulk'
    index: privilege-siem-events
    # The write-only user cannot call GET /, so name the version instead of letting Cribl probe it.
    elasticVersion: '7'
    authType: basic
    username: 'cribl_siem'
    password: '<writer password>'
  devnull:
    type: devnull

Route

pipelines/route.yml
routes:
  - id: siem
    name: privilege-siem
    final: true
    disabled: false
    pipeline: siem_mask
    filter: __inputId=='elastic:in_elastic'
    output: es_siem
  - id: default
    name: default
    final: true
    disabled: false
    pipeline: main
    filter: "true"
    output: devnull
    description: Anything else is dropped

Pipeline: mask, promote, fix the index

pipelines/siem_mask/conf.yml
asyncFuncTimeout: 1000
functions:
  # 1. Mask secrets in every field, including nested objects.
  - id: mask
    filter: "true"
    disabled: false
    conf:
      rules:
        # "<name containing password / secret / token / apikey / accesskey / virtualkey / providerkey>": "<value>"
        - matchRegex: /("\w*(?:password|passwd|secret|token|apikey|api_key|accesskey|virtualkey|providerkey)\w*"\s*:\s*")[^"]+(")/gi
          replaceExpr: "`${g1}***${g2}`"
        - matchRegex: /sk-[A-Za-z0-9_-]{16,}/g
          replaceExpr: "'sk-***'"
        - matchRegex: /Bearer\s+[A-Za-z0-9._~+\/=-]{8,}/g
          replaceExpr: "'Bearer ***'"
        - matchRegex: /eyJ[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}/g
          replaceExpr: "'***jwt***'"
      fields:
        - "*"
      depth: 5
  # 2. Promote the fields people filter on to the top level (runtime events keep them inside Data).
  - id: eval
    filter: "typeof Data === 'object' && Data !== null"
    disabled: false
    conf:
      add:
        - {name: gw_user, value: Data.User}
        - {name: gw_agent_key, value: Data.AgentKey}
        - {name: gw_app, value: Data.App}
        - {name: gw_policy_ids, value: Data.PolicyIDs}
        - {name: gw_decision, value: Data.Decision}
        - {name: gw_decision_reason, value: Data.Reason}
        - {name: gw_stage, value: Data.Stage}
        - {name: gw_target, value: Data.Target}
        - {name: gw_flow, value: Data.Flow}
        - {name: gw_request_id, value: Data.RequestID}
        - {name: gw_tenant, value: Data.Tenant}
      # Defence in depth: never store these headers if they ever appear.
      remove:
        - "Data.Headers.Authorization"
        - "Data.Headers['Proxy-Authorization']"
        - "Data.Headers.Cookie"
        - "Data.Headers['Set-Cookie']"
        - "Data.Headers['X-Api-Key']"
  # 3. Always write to one index (Privilege names its own, which your writer role does not cover), and drop Cribl's _time.
  - id: eval
    filter: "true"
    disabled: false
    conf:
      add:
        - name: __index
          value: "'privilege-siem-events'"
      remove:
        - _time
Two things that cost us time.
  • Cribl's Elasticsearch source accepts only _bulk requests (/_bulk and /<index>/_bulk) and only one authentication mode. A single-document write gets 404 could not find parser. Privilege uses _bulk, so this is fine here.
  • The mask function turns every value it visits into a string, even when no rule matches. That is harmless for the audit events (their Data fields are text in the index anyway). If you also ingest events with real numbers or booleans, list those field names before the "*" in the field list with a ! prefix (for example "!HTTPStatus"). Cribl takes the first match, so the order matters.

Step 4. nginx: the authentication front

Optional if you use username and password only. In that case set the Cribl source's authentication to Basic, expose it through your TLS front, and skip this step (see "Adapt it to your environment").

Cribl's Elasticsearch source takes one auth mode and does not accept the ApiKey scheme, but Privilege can send either Basic or ApiKey. A small nginx in front checks the credential and lets Cribl listen on loopback with no authentication of its own, so nothing can reach Cribl except through nginx.

/etc/nginx/conf.d/default.conf
map_hash_bucket_size 512;                       # credential strings are longer than nginx's default 64-byte bucket

# Auth scheme names are case-insensitive (RFC 7235): normalise before comparing.
map $http_authorization $auth_norm {
    ~*^basic\s+(?<c>.+)$     "Basic $c";
    ~*^apikey\s+(?<c>.+)$    "ApiKey $c";
    default                  $http_authorization;
}

map $auth_norm $siem_authed {
    default                  0;
    "Basic <base64 of privilege:password>"   1;     # printf 'privilege:%s' "$PW" | base64 | tr -d '\n'
    "ApiKey <your API key>"                  1;
}

server {
    listen 9200;
    client_max_body_size 20m;

    location / {
        default_type application/json;
        if ($siem_authed = 0) {
            return 401 '{"message":"Access denied"}';
        }
        proxy_set_header Authorization "";      # Cribl runs with no auth of its own
        proxy_set_header Host $host;
        proxy_http_version 1.1;
        proxy_pass http://127.0.0.1:9201;
    }
}

Generate this file from your secrets at deploy time. Do not commit it. Keep it readable only by root.

Step 5. Run it

nginx and Cribl must share a network namespace, so that nginx can reach Cribl on 127.0.0.1:9201. Publish only nginx's port 9200.

One host with Docker

Shell
# Cribl: configuration lives in ./cribl-local (inputs.yml, outputs.yml, pipelines/...). No port is published for 9201.
docker run -d --name cribl -p 127.0.0.1:9200:9200 -v "$PWD/cribl-local:/opt/cribl/local" cribl/cribl:4.13.0

# nginx joins Cribl's network namespace, so it can reach 127.0.0.1:9201 and owns the published 9200.
docker run -d --name nginx --network container:cribl -v "$PWD/nginx:/etc/nginx/conf.d:ro" nginx:1.27-alpine

Put your TLS terminator (a reverse proxy or load balancer with a real certificate) in front of 127.0.0.1:9200.

Kubernetes

  • One Deployment, one pod, two containers (nginx on port 9200 and cribl); they share the pod's network automatically.
  • An init container renders the Cribl and nginx configuration from your Kubernetes Secrets into emptyDir volumes, so no credential is ever in a ConfigMap or in git.
  • Expose only the nginx port through a Service and an HTTPS Ingress. Give the Cribl admin UI (port 9000) no Service; reach it with kubectl port-forward.
  • Readiness: a TCP probe on 9200 for nginx and an HTTP probe on 127.0.0.1:9201 for Cribl.
  • Use a Recreate strategy for a single replica, and expect a short gap in delivery on every deploy (see the limits below).
Cribl admin password. Cribl regenerates its user file as admin/admin when its local directory is empty at start. If you keep the directory on a persistent volume, set the password once in the UI. If you rebuild it on every start (as above), have a small sidecar set the password through Cribl's API from a secret on each start.

Step 7. Verify

Replace the placeholders. Read with an account that can read the index, not with the writer.

Shell
# 1. The endpoint refuses strangers and accepts the Privilege credential
curl -s -o /dev/null -w '%{http_code}\n' https://siem.example.com/                           # expect 401
curl -s -o /dev/null -w '%{http_code}\n' -u privilege:<password> https://siem.example.com/   # expect 200

# 2. Events are arriving (after a Health Check, or any change in the console)
curl -s -u <reader>:<password> 'https://<elasticsearch-host>:9200/privilege-siem-events/_count?pretty'
curl -s -u <reader>:<password> 'https://<elasticsearch-host>:9200/privilege-siem-events/_search?size=3&sort=@timestamp:desc&pretty'

# 3. The writer cannot read (expect 403)
curl -s -o /dev/null -w '%{http_code}\n' -u cribl_siem:<writer password> 'https://<elasticsearch-host>:9200/privilege-siem-events/_count'

Then check three things in a few stored events: secrets show as *** where a key or password would be, cribl_pipe is set, and the gw_* fields are present on runtime events.

In Cribl, Destination failed warnings in the log mean Elasticsearch refused something (usually an index the writer role does not cover).

Prompt logging

The Privilege Prompt Logging page controls whether prompts, tool calls and (optionally) responses are recorded, and for which surfaces (LLM traffic, MCP tool calls, agent-to-agent messages, coding agents). It also holds a size limit (default 65,536 bytes, maximum 131,072 per record), a public key and a key id.

How it protects the content

  • Every recorded item is encrypted to a public key that you hold (an X25519 key; HPKE, RFC 9180). Privilege cannot read the records. Only the private key opens them.
  • Make the key pair in the console (Generate Key Pair) or bring your own X25519 key as a JWK. Save the private half in a password manager at once. Privilege keeps no copy, and without it the records cannot be read.
  • The key id is recorded on every record, so after a rotation old records still open with the retired key.

What your SIEM receives (observed)

Records arrive as prompt-log events: the readable details plus the sealed content. This was checked with a real prompt that contained a unique marker: the marker was in none of the events, and no part of the prompt was readable in any Content field.

FieldContent
App, User, AgentKey, KeyType, PrincipalKind, TenantWho and what, in the clear
RequestID, Direction, Flow, Bytes, UnitCountWhich request, request or response, which surface, size
ContentThe sealed content (ciphertext, base64)
EncThe encapsulated key (32 bytes, base64); a request and its response share one
AlgObserved: HPKE-X25519-SHA256-AES256GCM-EXPORT
KeyIDWhich of your keys sealed it, for example prompt-log-<date>-<id>
Plan for it.
  • The SIEM holds every sealed prompt. Whoever has the private key and can read the index can open all of them. Restrict both, and keep the private key out of the SIEM's reach.
  • Volume: a request and its response are two records each. In light test traffic about 2.4 records a minute were seen; with real use and larger prompts, size the index and its retention for it.
  • Cribl does not alter the ciphertext.
  • Opening a record was tested end to end: a record read from the index opened with the private key and returned the original prompt. Each record is an HPKE (RFC 9180) encapsulation to your X25519 public key (suite HPKE-X25519-SHA256-AES256GCM-EXPORT); a 44-byte secret derived from the record's Enc value with the context <RequestID>|<Direction> gives the AES-256-GCM key (first 32 bytes) and nonce (last 12), and the same context is the authenticated data. Open the request and the response separately.
  • Check the Public key box, not only the Key id. In the console the Key id is a label recorded on each row, while the Public key box is what records are sealed to. If the box still holds another key, records carry your key id yet will not open with your private key. After saving, reload the page, confirm the box shows your public key, send one test call, and open its records before relying on the setup.
  • The Prompt Logging page also describes reading records in the console's Agent Insights → Prompts view, with the private key entered in your browser (that view was not tested here).

Security checklist

  • Endpoint over HTTPS only; certificate valid for the name Privilege uses.
  • Cribl's port 9201 is bound to 127.0.0.1 and not published. nginx is the only way in.
  • Credentials generated randomly, stored in a secret manager, never in git or a ConfigMap, rotated on a schedule.
  • The Elasticsearch writer is write-only on the one index family. No read, no other indices.
  • Test the refusals: no credential, a wrong password and a wrong key are all 401.
  • The index is readable only by people who need it (events carry user ids, device details and client IP addresses; prompt-log carries sealed content).
  • No anonymous access on Elasticsearch or Kibana; port 9200 of Elasticsearch is not on the public internet.
  • Cribl's admin UI has no public route and no default password.

Limits to know about

  • No queue. Events that arrive while Elasticsearch is down, or while the pod restarts, are lost. If you need no loss, enable Cribl's persistent queue on the destination, backed by a persistent volume (not tested here).
  • One replica gap. A single replica with a Recreate strategy leaves about a minute with no delivery on each deploy. If that matters, run two replicas with a rolling update behind the same Service (not tested here; keep the nginx and Cribl configuration identical in both).
  • Cribl's Elasticsearch source is _bulk only and takes one auth mode (hence nginx).
  • The index name is chosen by Privilege and cannot be set in the form; the pipeline overrides it.
  • Privilege sends from its cloud, so a private-network-only Elasticsearch needs the public front described here.
  • Rotating a credential means updating nginx (and the Privilege form) together.
Hosts, names and credentials in this guide are placeholders. Everything described was run in a test environment; limits and open points are stated where they apply.
